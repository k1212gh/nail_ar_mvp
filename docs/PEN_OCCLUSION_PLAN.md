# 펜 가림(Occlusion) 해결 계획 — 손톱 → 디자인 → 펜

> 작성 2026-07-22 (노트북 세션). **다른 PC에서 이어서 작업하기 위한 인수인계 문서.**
> 코드 현황: A단계 프로브는 `feat/pen-occlusion` 브랜치(`082f486`)에 있음. main에는 아직 미머지.

---

## 1. 문제

네일아트 **디자인 가이드**로 쓸 때, 손톱에 펜(또는 붓/도구)을 갖다 대면 레이어 순서가 뒤집힌다.

| | 순서 (뒤 → 앞) |
|---|---|
| **목표** | 손톱 → **디자인** → **펜** (펜이 디자인을 가림) |
| **현재** | 손톱 → **펜** → **디자인** (디자인이 펜을 덮어버림) |

디자인이 항상 최상단에 그려져서, 물리적으로 앞에 있는 펜을 가린다. 작업자가 **펜 끝이 디자인의 어디에 있는지** 볼 수 없어 가이드 기능이 무의미해진다.

---

## 2. 핵심 재정의 (가장 중요)

> **이건 깊이(depth) 문제가 아니라 마스킹(masking) 문제다.**

- GUIDE 앱은 **광학 시스루가 아니라 "비디오 루페"**다. 카메라 프레임을 온디바이스 텍스처로 받아(`m_Handler.UpdateT2d()`) 디지털 확대해서 한쪽 눈에 보여준다. → **펜은 이미 우리가 가진 프레임 안에 찍혀 있다.**
- 따라서 **펜이 있는 픽셀에서 디자인을 안 그리기만 하면**, 그 자리에 (이미 프레임에 있는) 펜이 드러난다.
- 순수 광학 시스루 모드여도 원리는 같다 — 웨이브가이드는 가산(additive)이라 **안 그리면 실물이 그대로 보인다.** 즉 어느 모드든 **마스킹이 정답 프리미티브**다.

**한 줄 공식**

```
design_alpha = nail_mask AND (NOT pen_mask)
```

재료는 이미 다 있다. 손톱 마스크는 에지 YOLO가 이미 돌려주고, 펜은 프레임 안에 있다.
**남은 건 "펜 마스크를 어떻게 얻느냐" 하나뿐이다.**

## 3. 조사해서 확인한 아키텍처 (이어서 작업할 때 필요)

### 3.1 앱 정체
- `NailGuide` = `com.DefaultCompany.NailGuide`, 빌드 정의 **`MIRROR_APP;GUIDE_APP`** (`Nail/Assets/Editor/CIBuild.cs` → `BuildGuideDev`).
- 정의가 둘 다 켜져서 → **`MirrorMesh` 모드로 부팅** + `m_GuideOn=true`(루페) + `SetMono(1)`(**왼쪽 눈 단안**).
- 단안은 설계 의도임(보석세공사 루페 패턴): 한 눈은 확대 가이드, 다른 눈은 실물 손톱.

### 3.2 카메라
- `camW=640, camH=400` (`NailARController.cs` 상단). 주석에 명시: **웨이브가이드에 단일(single)로 렌더되는 유일한 크기.** 그보다 크면 눈당 1280으로 더블링됨 → **640×400 유지할 것.** (단안이어도 per-eye 현상이라 동일)

### 3.3 에지 서버 (`web/edge_serve.py`)
- `_infer_yolo(img)` → 손톱 리스트 반환. 각 항목:
  `cx, cy, ex, ey(축 단위벡터), len, wid, contour(폴리곤 점 배열)`
- 포트: **8443**(HTTPS `/infer`) / **8444**(raw TCP 소켓 — **앱이 실제로 쓰는 빠른 경로**) / **8080**(무선 모니터)
- 모니터: `_update_monitor()`가 프레임에 컨투어(초록)·중심(빨강)·텍스트를 그려 `/last.jpg`로 서빙. `/monitor` 가 뷰어 페이지.

### 3.4 ★ 디자인 합성 방식 (가장 중요한 제약)
디자인은 **온디바이스에서 합성**되며, **픽셀 마스크를 쓰지 않는다**:

- `NailOverlayRenderer.ComputeTargets()` — 손톱의 **기하값만**(`cx, cy, len, wid, 축`) 받아서 그 위치에 **사각 스프라이트**를 회전·스케일해 얹는다. `calibOffset` 더하고 `designScale` 곱하는 정도.
- `NailMeshRenderer` — 손가락별로 **구운(baked) 곡면 메쉬**를 얹는다. `calibOffset`, `alongTip` 적용.
- → **손톱 외곽으로 오려내는 per-pixel 마스킹 경로가 아예 없다.**

**결론: 펜 가림을 하려면 셰이더 레벨에서 새 마스킹 경로를 만들어야 하고, 이는 Unity 재빌드가 필수다.**
(에지에서만으로는 못 끝낸다 — 에지는 마스크를 *만들어 보내줄* 수는 있어도, *적용*은 디바이스가 해야 함)

### 3.5 빌드 환경
- Unity **2022.3.36f1** (프로젝트 요구 버전과 일치), Android 모듈 필요.
- 빌드: `Unity.exe -quit -batchmode -projectPath <repo>/Nail -executeMethod CIBuild.BuildGuideDev -logFile <log>`
- 산출: `Nail/NailGuide_AUTO.apk` (~38MB, IL2CPP/ARM64, **dev 빌드**라 `adb logcat -s Unity`에 `[NailAR]` 로그 나옴)
- **빌드 시간 ~15~20분** → 디바이스 변경은 몰아서 한 번에 할 것.

## 4. 해결 방안 스펙트럼 (간단 → 복잡)

### Tier 0 — 임시방편 (진짜 가림 아님)
- 디자인 **반투명/가산 블렌드** → 펜이 비쳐 보임. 근본 해결 X.
- 펜 접촉 감지 시 디자인 **순간 디밍/숨김**. 조잡하지만 접촉 순간은 자연스러움.
- 펜을 옆에서 대도록 **접근각 유도**. 코드 0, 대신 취약.
> 시연 안전망으로만.

### Tier 1 — 외형 기반 컷아웃 (가장 쉬운 *진짜* 해결)
- 손톱 마스크 **안에서** 픽셀을 색/밝기로 "손톱면 vs 펜"으로 판별 → 펜이면 디자인 알파 0.
- 구현: 온디바이스 셰이더가 피드 텍스처를 같은 UV로 샘플해 크로마/루마 키 → `clip()`.
  (피드와 디자인이 **같은 캔버스로 함께 변환**되므로 좌표가 일치함 → 매핑이 깔끔)
- 장점: ML 불필요, 저지연. 단점: **색 의존** — 펜이 손톱/피부색과 비슷하면 실패.

### Tier 2 — 펜 명시 검출 (중간, 견고) ← **본命 후보**
- **고전 CV**: 펜 = 길고 곧은 고대비 막대 → 에지 + 허프라인/최소사각. 이미 YOLO 도는 에지 서버에 얹기 좋음. **형태 기반이라 색 무관.**
- **세그 모델에 "펜/도구" 클래스 추가 학습**: 손톱과 함께 펜 인스턴스 마스크를 직접 출력. 가장 견고하나 데이터 수집 + 학습 필요.

### Tier 3 — 깊이/기하 기반 (복잡, "정석")
- 펜이 손톱면보다 앞임을 깊이로 판정.
- **문제**: 현재 앱 깊이는 `depthK / avgNailLenPx` **단안 휴리스틱**뿐, 조밀 depth map이 없음. 스테레오 disparity나 학습형 monocular depth 필요.
- 근거리 스테레오는 노이즈·캘리브 난이도가 높음. **펜 하나 가리자고는 과함.**

### Tier 4 — 전체 장면 분할 (최고 복잡)
- 손톱/손가락/도구 시맨틱 세그 + 시간 일관성. 임의 물체 가림 가능하나 **오버킬.**

## 5. 채택한 진행 계획 (재빌드 비용을 한 번만 내는 순서)

느린 Unity 재빌드(~15~20분) 때문에, **"펜이 잘 검출되나?"라는 핵심 리스크를 재빌드 없이 먼저 없앤다.**

### A단계 — 에지에서 펜 마스크 프로토타입 + 모니터 시각화 (재빌드 0) ← **현재 여기**
- Python/OpenCV로 펜 후보를 계산해 **모니터 화면에 색으로 덮어** 검출 품질을 눈으로 검증.
- 빠른 반복(서버 재시작만). 검출이 안정될 때까지 여기서 튜닝.

### B단계 — 온디바이스 셰이더 컷아웃 (재빌드 1회)
- A에서 확정된 마스크를 디자인 알파에서 빼기. 그때 한 번만 빌드.

## 6. A단계 구현 현황

**브랜치 `feat/pen-occlusion`, 커밋 `082f486`** (main 미머지)

`web/edge_serve.py`에 추가:

- **`_pen_probe_overlay(im, nl)`** — 손톱 컨투어를 채워 영역 마스크를 만들고 **25×25 팽창**(펜이 손톱 밖으로 삐져나오므로) 후, 그 안에서 3가지 단서를 각각 다른 색으로 오버레이:

  | 색 | 단서 | 의도 |
  |---|---|---|
  | 🔵 파랑 | `gray < 90` (어두움) | 검정/금속 펜 몸통 |
  | 🟠 주황 | `sat < 40` (저채도) | 회색 플라스틱/금속 (피부는 채도 높음) |
  | 🔴 빨강 | Canny 에지 + 팽창 | 펜 몸통 윤곽/직선 |

- **`_update_monitor()`** 안에서 손톱을 그린 **직후·회전 직전**에 호출.
- 토글: 환경변수 **`PEN_PROBE=0`** 으로 비활성화. **진단 전용 — 렌더링 경로는 아직 하나도 안 건드렸음.**

### 설계 의도
펜의 실제 생김새(색·재질)가 **아직 미확정**이라, 특정 방식에 커밋하지 않고 **여러 단서를 동시에 보여줘서 "실제 펜에 뭐가 잘 달라붙나"를 눈으로 고르게** 했다. 이게 A단계의 목적이다.

### 검증 상태
- ✅ 문법 검증 통과 (`py_compile`)
- ✅ 오프라인 실행 검증 — 모듈 import + 함수 실행에 에러 없음
- ❌ **시각 검증 미완** — 저장 프레임 `_last_frame.jpg`에 손이 없어(`nails=0`) 오버레이가 안 그려졌고, 세션 도중 **안경 USB가 끊겨** 라이브 확인을 못 함.

## 7. 다음에 할 일 (desktop에서 이어서)

1. **[A단계 마무리] 단서 고르기**
   안경 연결 → 서버 실행 → 모니터에서 **손 + 펜**을 대고, 펜에 **어느 색이 잘 얹히는지** 확인.
   동시에 **손톱에 잘못 얹히는 색(오탐)** 도 기록 — 그건 걸러야 함.

2. **펜 마스크 정제**
   고른 단서에 **형태 필터** 추가: 길쭉함(장축/단축 비), 직선성, 최소 면적 → 손톱 표면의 그림자·무늬 오탐 제거.
   결과는 **폴리곤(컨투어)** 형태로 뽑는 게 좋음(전송 저렴).

3. **마스크를 디바이스로 전달**
   추론 응답 `res`에 펜 정보를 추가 (예: `"pen": [[x,y],...]` 폴리곤, 또는 손톱별 `penPoly`).
   ⚠️ 전 프레임 비트마스크는 대역폭·지연 부담 → **폴리곤 권장.**

4. **[B단계] 온디바이스 컷아웃 (재빌드 1회)**
   - `NailOverlayRenderer`(스프라이트)와 `NailMeshRenderer`(메쉬) **양쪽** 머티리얼에 마스킹 적용.
   - 방법 두 갈래:
     - (a) 셰이더가 **피드 텍스처를 직접 샘플**해 키잉 (Tier 1) — 서버 전송 불필요
     - (b) 서버가 준 **펜 폴리곤을 스텐실/알파 마스크로 래스터화**해 `clip()` (Tier 2)
   - 캔버스 변환(회전/미러/줌)이 피드와 디자인에 **공통 적용**되므로 UV 매핑은 일관됨 — 이 점을 활용할 것.

5. **빌드 & 검증**
   `CIBuild.BuildGuideDev` → `adb install -r` → 안경에서 펜 대보고 레이어 순서 확인.

## 8. 재현/실행 방법

```powershell
# 0) 환경 (노트북엔 anaconda의 mediapipe가 깨져 있어 venv 사용)
py -3.11 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 1) 에지 서버 (펜 프로브 포함)
.\.venv\Scripts\python.exe web\edge_serve.py
#   → "워밍업 완료" + 배너 뜨면 준비 완료
#   → 프로브 끄려면:  $env:PEN_PROBE="0"  후 실행

# 2) 안경 연결 (USB)
adb devices                      # device 로 떠야 함
adb reverse tcp:8443 tcp:8443
adb reverse tcp:8444 tcp:8444    # ★ 앱이 쓰는 소켓 포트
adb shell input keyevent KEYCODE_WAKEUP
adb shell wm dismiss-keyguard
adb shell svc power stayon true
adb shell monkey -p com.DefaultCompany.NailGuide -c android.intent.category.LAUNCHER 1

# 3) 모니터에서 프로브 확인 (같은 WiFi면 폰에서도)
#    http://<PC-IP>:8080/monitor
```

**정상 동작 신호**: 서버 로그에 `infer bytes=... nails=N ms=...` — `nails>0`이면 검출 성공.
`nails=0`만 계속되면 손 거리(25~40cm)·조명 확인.

**자주 겪은 함정**
- 안경이 **잠금화면(Doze)** 으로 넘어가면 앱이 안 보임 → `KEYCODE_WAKEUP` + `dismiss-keyguard` + `stayon true`.
- `adb install` 시 데몬 재시작으로 **기기를 놓치는 경우** 있음 → USB 재연결.

## 부록 A. 터치패드 하드웨어 메모 (튜너 작업 중 확인)

- RayNeo는 **왼쪽 템플 = 시스템 볼륨**, **오른쪽 템플 = 앱 터치패드**로 OS가 분리한다.
  → 왼쪽 스와이프는 **앱에 도달하지 않는 게 기본**. "왼쪽=줌" 같은 매핑은 그냥은 불가.
- 왼쪽을 쓰려면 `KEYCODE_VOLUME_UP/DOWN`을 커스텀 Activity의 `onKeyDown`에서 **가로채야** 함(인앱 볼륨 조절은 포기).
- 그래서 현재 튜너는 **오른쪽 패드 하나로**: **탭 = 조절 대상 순환**(정합 X → 정합 Y → 줌 가중치 → alongTip), **스와이프 = 값 ± 조절**. HUD에 `[tap]/[swipe]/[key]` 입력소스를 찍어 **어떤 경로로 입력이 들어오는지 정찰**도 겸한다.
- 이 하드웨어 제약을 감안하면 **"오른쪽 패드 + 탭 전환"은 타협이 아니라 정답**에 가깝다.

## 부록 B. 가이드 확대(줌) 파라미터

- `guideTarget` — 손톱이 **화면 높이의 몇 %**를 채울지 (기본 `0.45`). 이게 사실상 "확대 가중치".
- `guideAuto` — 손 거리와 무관하게 그 크기를 자동 유지 (기본 on).
- `guideZoom` 기본 3배, `guideZoomMin=1.5` ~ `guideZoomMax=8` 로 클램프.
- 런타임 변경: `python web/push_calib.py pkg=com.DefaultCompany.NailGuide guideTarget=0.9 guideZoomMax=12`
  (앱이 0.7초 폴링으로 자동 반영. 온디바이스 튜너 값은 PlayerPrefs에 영속)
